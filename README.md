# ⚖️ 两两决策台（Pairwise Decision Desk）

粘贴 3～12 个候选项，逐对比较并记录胜者或平局，系统按 **Schulze 最强路径法** 实时计算排名。

- 后端：FastAPI + SQLite（标准库 `sqlite3`，无额外依赖）
- 前端：原生 HTML / CSS / JavaScript（单页，无构建步骤）
- 进度持久化：评审记录存入 SQLite，浏览器刷新后自动恢复

## 🚀 启动（唯一命令）

```bash
docker compose up --build
```

该命令会自动完成：构建镜像 → 安装依赖 → 启动服务（首次启动时自动创建 SQLite 数据库与表结构）。

启动后访问：

| 项目 | 地址 |
| ---- | ---- |
| 网页 | <http://localhost:8000> |
| API 文档（Swagger） | <http://localhost:8000/docs> |

停止：`Ctrl + C`；删除持久化数据：`docker compose down -v`。

## 🖱️ 使用说明

1. **录入候选项**：每行一个，3～12 个，名称不可重复，点击「开始评审」。
2. **逐对评审**：界面依次展示每一对组合，点击左侧 / 右侧按钮选择胜者，或点「平局」。
   快捷键：`←` 左边胜、`→` 右边胜、`↓` 平局、`Ctrl+Z` 撤销。
3. **实时排名**：按 Schulze 最强路径法计算，并列的候选项归入同一名次组（以「＝」连接，黄色徽标）。
4. **尚未比较的组合**：以标签形式列出所有待比较组合。
5. **下一对推荐**：「下一对推荐」卡片自动给出当前最值得优先评审的组合，
   展示推荐理由（影响分）与「左胜 / 平局 / 右胜」三种结果各自的排名预览。
   点击「立即评审这一对」可跳转到该组合直接判定（判定接口接受任意待比较组合），
   跳转后随时可点「返回原顺序」；不跳转则完全按原顺序继续，二者互不影响。
   每次新增判断、撤销、复核或批量改判后，推荐都会自动重新计算。
6. **胜负矩阵**：行 vs 列，`✓` 行胜、`✗` 行负、`＝` 平局、`·` 未比较。
7. **循环冲突复核**：当严格胜负关系构成环（如 甲胜乙、乙胜丙、丙又胜甲）时，「循环冲突复核」
   卡片自动出现，展示最短冲突环路径；环上组合在卡片与胜负矩阵中同步以红色高亮。
   - **手动改判**：点击卡片中的组合标签或矩阵中的红色格，在展开的面板中重新选择胜者或平局：
     后端**原位替换**该组合的记录，进度总数与已完成数保持不变，排名、待比较组合与
     下一条冲突立即重算；若冲突解除，卡片自动消失。
   - **最少改判方案**：卡片同时给出后端基于当前严格胜负边计算的建议——把**最少数量**的组合
     批量改为平局即可消除全部有向环（平局与未比较组合不参与计算）。面板列出建议组合、
     每条受影响结果（原胜负 → 平局）以及应用后的排名预览；建议组合在矩阵中以黄色高亮。
     存在多个最优方案时，按**判断记录顺序**稳定选择（优先改判更早记录的组合）。
     点击「确认并批量改为平局」一次确认后批量应用；更新在单个 SQLite 事务中完成，
     判断记录 id、进度统计与撤销顺序均不变，随后自动重算排名与冲突。无冲突时不显示建议。
8. **撤销 / 重置**：「撤销上一判断」回退最近一次判断；「重置本轮」清空本轮全部判断（保留候选项）；「新一轮」重新录入候选项。
9. 刷新页面后进度自动恢复（会话 ID 存于浏览器 localStorage，数据存于 SQLite）。

## 🧮 排名算法

Schulze 最强路径法：路径强度为路径上最弱一环，最强路径取各路径最大值。
计票约定：胜 = 1，平局 = 0.5（双向），未比较 = 0。
候选项 X 严格优于 Y 当且仅当 `p(X,Y) > p(Y,X)`，相等则并列，据此划分有序并列组。

## 🎯 下一对优先级推荐

- 对每个**尚未比较**的组合，后端分别模拟「左胜 / 右胜 / 平局」三种结果并重算 Schulze 排名。
- **影响分**：在所有候选对 {X, Y} 中，其相对次序状态（X 前 / X 后 / 并列，取自排名分组）
  在三种模拟结果之间发生变化的候选对数量。影响分越高，该组合的结果对最终排名的决定性越强。
- 推荐**影响分最高**的组合；同分时按现有待比较顺序（候选录入顺序）取先者，保证推荐稳定可复现。
- 状态接口新增 `next_pair` 字段：`a` / `b` 推荐组合，`impact` 影响分，
  `candidate_pairs` 候选对总数（影响分上限），`previews` 三种结果各自的排名预览；
  全部比较完毕时为 `null`。新增判断、撤销、复核、批量改判后随状态自动重新推荐。
- 全部模拟在内存中完成：**不写入数据库、不改变完成进度**（进度仍只统计实际判断记录）。
- 为支持一键跳转评审，`POST /api/sessions/{id}/judgments` 现在接受**任意尚未比较**的组合
  （组合按候选录入顺序存储，`result` 相对请求中先出现的 `a` 解释）；
  已判定组合仍返回 409，原有按顺序评审的调用方式不受影响。

## 🔄 循环冲突检测与最少改判方案

- 仅以**严格胜负**判断构成有向边（胜者 → 败者）；平局与未比较的组合不成边。
- 在该有向图中寻找**最短有向环**作为冲突路径，随状态接口返回（`conflict` 字段，
  含环上候选项序列 `cycle` 与环上各组合 `edges`）；无环时为 `null`。
- 存在多个同长度环时，按候选录入顺序稳定选择（环以其最早录入的成员开头，取字典序最小者）。
- 复核修改通过 `PUT /api/sessions/{id}/judgments` 原位更新记录（行 id 与记录数不变），
  因此进度统计与撤销顺序不受影响，返回状态中已包含重算后的排名与下一条冲突。
- **最少改判方案**：把严格胜负边改为平局等价于从有向图中删边，最少改判数即严格胜负图的
  **最小反馈弧集**大小（等价于寻找「逆向边」最少的顶点排列，用子集 DP 对 n ≤ 12 精确求解）。
  状态接口的 `suggestion` 字段随冲突一同返回：
  - `pairs`：建议改判的组合，`change_count`：改动数；
  - `affected`：每条组合的受影响结果（`from` 原严格胜负 → `to` 平局）；
  - `preview_ranking`：应用后的 Schulze 排名预览。
  无冲突时 `suggestion` 为 `null`。存在多个最优方案时，严格边按**判断记录 id 顺序**编号，
  取编号集合字典序最小者，保证建议稳定、可复现。
- 批量应用通过 `POST /api/sessions/{id}/resolve-conflicts` 完成：所有 `UPDATE` 在
  **单个 SQLite 事务**中执行（任一组合与当前建议不符或已非严格胜负即整体回滚），
  只原位改判、不增删记录，因此判断记录 id、进度与撤销顺序不变；提交后重算排名与冲突。

## 📡 API 概览

| 方法 | 路径 | 说明 |
| ---- | ---- | ---- |
| POST | `/api/sessions` | 创建评审会话（body: `{"candidates": [...]}`） |
| GET | `/api/sessions/{id}` | 获取完整状态（进度、当前对、排名、矩阵、待比较组合、循环冲突、最少改判建议、下一对推荐） |
| POST | `/api/sessions/{id}/judgments` | 记录判断（body: `{"a","b","result": "a"\|"b"\|"tie"}`）；接受当前对或任意待比较组合（用于推荐跳转） |
| PUT | `/api/sessions/{id}/judgments` | 复核修改：原位替换一条已判定组合的结果（body 同上），进度不变 |
| POST | `/api/sessions/{id}/resolve-conflicts` | 一次确认批量应用最少改判方案：单事务把建议组合改为平局，重算排名与冲突 |
| POST | `/api/sessions/{id}/undo` | 撤销最近一次判断 |
| POST | `/api/sessions/{id}/reset` | 重置本轮全部判断 |
